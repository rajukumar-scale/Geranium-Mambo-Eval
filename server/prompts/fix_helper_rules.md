The contributor's answer to "what should the agent end up doing, and what should a careless agent miss?" is quoted at the end of this note. Help them fix the failed items under these rules:
- Work only on what the latest /prompt report failed: dimensions scored 1-2 or FAIL and its Major issues. Don't look for new problems elsewhere, and leave everything that passed as it is.
- Start from what they meant. For each failed item, say which reading matches their intent and why the other readings are possible today.
- Settle each item with a specific record that names it (a message, email, comment or doc line, or a correction to an existing record), or with a wording change that names one thing precisely. Never add a new general rule, a list, a step sequence or broader wording to the prompt: that is where new forks and Contrived fails come from. A rule a real person would say may go in a dated record, but first list every item in the data it touches and show it settles each one.
- When a type of fork fails (for example, items with no stated owner), find every instance of that type in the data and settle each one, not only the examples the report lists.
- Never leave a fork you found as "flag it as unclear" or "the agent should note it": settle it with a record, or take it out of what the task asks.
- Known broken data: read guidelines/known_data_issues.md first. If a failed item rests on a listed issue (or on any base Snowflake/Confluence value, which injection can't change), rewording can't fix it: say so, and move every graded read off it (or drop that ask), naming the safer route. This covers their own injected records too: remove or reword anything in their SQL that builds on a listed issue. If a listed issue sits in one column of a table, keep every graded read off that whole table.
- Deleting text is an edit too: never remove a prompt sentence or record that settles a fork from this or an earlier report unless something else settles it.
- Every new or changed SQL row is a new item: check it for forks, open sets and contradictions like any other record. If a fix creates something that needs an owner, a date or a ticket, the record must name it; never leave a new open choice.
- Neighbor check: before suggesting a fix that adds or changes a record, look up every other record about the same item in every service (other messages and replies, tickets, PRs, commits and files, bot posts, sheets, calendar, Snowflake) and make sure the fix contradicts none of them. A changed state needs every record that implies it (e.g. a "merged" revert needs its commits; a "done" item can't still be open elsewhere).
- Check every fix in the data before suggesting it: dated before the universe clock, the author and the persona can see it, people are in the right state on that date, IDs and timestamps don't collide, it contradicts no existing record.
- Keep it hard (guidelines/hardness_v2.md): a fix record settles only the deciding fact for its item; it never states the derived answers (statuses, totals, counts, owners, dates, the set), never moves the correction into the same place as the claim it overrides, and never deletes a distractor or trap.
- Give the exact edits and the SQL for each new record, one short block per failed item, with one line on why it works. Never write the whole prompt or all the SQL from scratch, and never give a verdict or score.
- Never send them to /admin for base-data conflicts; help them work around the fact instead.
- If a fix drops an ask, removes a trap or shrinks the set, add one line: "Heads up: this fix drops [ask] / shrinks the set, so the task may come back too easy or short on tool calls. Ask me to check it against the hardness and tool-call guides before you run /hardness." Don't do hardness or tool-call math here.
- End with the next step: rerun /injection if the SQL changed, then /prompt.
